**Koreksi wajib untuk rencana:**

3. **Verifikasi wajib berbasis hash**, bukan keberadaan berkas: `hash(SOUL.md) == 02b649a5dcff1318…`. "Berkas ada" adalah pemeriksaan palsu — drill ini membuktikannya.
4. Setiap berkas yang di live-nya berupa **symlink** harus diperiksa terpisah (bukan hanya SOUL.md).

### A.3 Catatan teknis dari drill
- `hermes backup` → 201 MB; cakupan bersih → 116 MB; `state.db` 242 MB → 98,5 MB terkompresi
- `hermes import` **tidak** mengembalikan `gateway_state.json`, `gateway.pid`, `cron.pid`, `gateway.lock`, `processes.json` (memang disengaja — state runtime)
- Zip = tempat kedua kredensial berada → **hapus setelah drill/verifikasi** (sudah dilakukan)

### A.4 Perilaku `hermes import` yang wajib diketahui (dari output lengkap drill)

Empat hal ini menjawab langsung pertanyaan "apa yang masih harus dilakukan **setelah** import sukses":

1. **Kode hermes-agent TIDAK ikut backup.** Output import: *"The hermes-agent codebase was not included in the backup. If this is a fresh install, run: `hermes update`"* → memasang Hermes (langkah 5) memang prasyarat terpisah; restore hanya memulihkan **konfigurasi & data**, bukan mesinnya.
2. **Layanan gateway TIDAK dipasang otomatis.** Output: *"Restored into a non-default home; leaving the gateway service alone to avoid clashing with the install at ~/.hermes. To start a gateway for this home, run: `hermes gateway install`"* → langkah 11 (launchd / systemd / Task Scheduler) tetap wajib; restore konfigurasi tidak menghidupkan apa pun sendiri.
3. **3 berkas state runtime mesin target dipertahankan, bukan ditimpa:** `gateway.lock`, `gateway_state.json`, `processes.json` → restore tidak membawa state proses dari mesin lama (perilaku yang benar).
4. **Pelajaran verifikasi: alat bisa berbohong.** Pada drill yang sama, perintah pertama melaporkan **`skill: 0`** sementara pemeriksaan ulang dengan Python melaporkan **202**. Angka 0 itu artefak alat — `find` di shell ini ter-alias ke `fd`, yang tidak menerima argumen `-name`, sehingga mengembalikan kosong tanpa error. Dua alat, dua jawaban, untuk berkas yang sama.

   **Konsekuensi untuk `verify.sh`:** setiap pemeriksaan harus memakai **satu metode yang sudah diuji**, mencetak metode yang dipakai, dan **gagal keras** kalau perintahnya tidak menghasilkan apa pun — bukan melaporkan `0` seolah-olah hasil sah. Ini kelas bug yang sama dengan `SOUL.md`: "nol" dan "ada" sama-sama bisa menyesatkan tanpa pembanding.

## C. Portabilitas path & kredensial

### C.1 Path absolut — akar kegagalan terbesar
- **75 berkas** konfigurasi memuat `/Users/zaryu` (launchd plist, `scripts/`, banyak `SKILL.md`)
- 31 berkas di ekosistem merujuk `Desktop/Niumination` absolut; `.hermes/.env` dirujuk 7 script
- **Aturan baru:** berkas di repo restore **tidak boleh** memuat path device-spesifik. Gunakan placeholder:
  - `{{HOME}}` → `$HOME` / `%USERPROFILE%`
  - `{{ECO}}` → `$HOME/Desktop/Niumination`
  - `{{HERMES_HOME}}` → `$HERMES_HOME`
- `restore.sh` melakukan substitusi **hanya pada berkas yang di-allowlist**, mencetak daftar berkas yang diubah, dan **dry-run secara default**
- 75 berkas itu tetap perlu perbaikan terpisah di sumbernya (bukan bagian repo restore) — dicatat sebagai utang di ekosistem

### C.2 Kredensial tidak boleh bergantung pada OS
- Keychain/libsecret/Credential Manager **tidak portabel** → semua rahasia yang dibutuhkan harus ada dalam bentuk berkas terenkripsi (`.age`)
- Yang hidup di OS keystore (mis. token `gh`) **berubah jadi langkah login ulang** → masuk checklist, bukan dianggap otomatis
- Enkripsi: **`openssl` (zero-install) atau `age` (satu binary per OS)** — keduanya tersedia lintas platform. Roundtrip `openssl enc -aes-256-cbc -pbkdf2` sudah **diuji LULUS** (hash identik)

### C.3 Line ending & atribut
- Repo restore **wajib** punya `.gitattributes`:
  `* text=auto eol=lf` · `*.sh text eol=lf` · `*.bat text eol=crlf` · `*.ps1 text eol=crlf` · `*.age binary` · `*.part-* binary`
- Temuan: 1 berkas CRLF di ekosistem (`skills/design/ui-ux-pro-max/scripts/search.py`) — tidak fatal, dicatat

## D. Koreksi arsitektur: jangan simpan blob besar di history git

**Cacat rev 2:** menjadwalkan backup 116 MB secara berkala ke dalam commit. Setiap commit menambah ~116 MB ke history → dalam ~6 minggu repo menembus 5 GB (hard limit GitHub), clone jadi tak terkendali, dan menghapusnya nanti butuh rewrite + force-push (persis masalah yang sudah pernah kita alami).

**Perbaikan untuk rev 3 — pisahkan tiga hal:**

| Isi | Tempat | Alasan |
|---|---|---|
| Skrip (`restore.sh`, `verify.sh`), `README`, `MANIFEST`, `RESTORE-PATHS.md`, patch (`*.patch`), checksum | **commit di git** (kecil, berversi, bisa di-review) | teks, tumbuh lambat |
| Blob besar: `hermes-backup.zip.part-*` (116 MB), `ecosystem-ignored.tar.zst.age`, `state.db` terkompresi | **aset GitHub Release** (tag `backup-YYYY-MM-DD`) | aset Release bisa diganti/dihapus **tanpa** menggelembungkan history git |
| Kredensial terenkripsi kecil (`*.age` < 1 MB) | boleh di commit (ciphertext) | kecil & perlu ada bersama skrip restore |

**Konsekuensi yang harus diterima:** repo git tidak lagi memuat seluruh data; `restore.sh` **wajib** mengambil aset Release lewat `gh release download`. Ini diperiksa `verify.sh`.

## H. Batas jujur

1. **Tanpa disk eksternal, L0 (OS/aplikasi) tetap tidak tertutup.** Pindah OS = instalasi manual; yang terbantu hanya daftar paket.
2. **Lintas OS bukan "salin-tempel jalan".** Dotfiles `stow`+zsh tidak berlaku di Windows; layanan butuh tiga implementasi.
3. **Keystore OS tidak portabel** → sebagian kredensial berubah menjadi langkah login manual.
4. **Repo privat menyimpan skrip, bukan data** (rev 3): restore bergantung pada aset Release yang harus benar-benar diunggah dan bisa diunduh.
5. **Backup ini tetap bersumber dari mesin yang sama** sampai benar-benar terunggah; kegagalan sync harus terlihat.
6. **Satu drill (macOS→macOS-home) belum membuktikan lintas OS.**
