# Supabase provisioning through Composio

Recipe for standing up a Supabase project and its schema when Supabase access is brokered by Composio (no Supabase CLI, no PAT in hand). Order matters; each step's output feeds the next.

1. **Confirm authorization, not just enablement.** `COMPOSIO_MANAGE_CONNECTIONS` for `supabase`; require `has_active_connection: true` and a `connected_account_id`. If absent, return a Connect Link (expires in minutes) and stop.
2. **`SUPABASE_LIST_ALL_ORGANIZATIONS`** → real `organization_id`. A slug or the literal string `personal` is rejected; the API wants the org id.
3. **`SUPABASE_LIST_ALL_PROJECTS`** → check for an existing project of that name before creating, and read the count against free-tier active-project quota. Names may already hold the account's quota.
4. **`SUPABASE_CREATE_A_PROJECT`** with a dot-free name (hyphens), a region chosen for the actual users, `plan`, `postgres_engine`, and `db_pass` — a 32-char random generated locally, stored mode 600, never printed.
5. **Poll `SUPABASE_GETS_PROJECT_S_SERVICE_HEALTH_STATUS`** until `db` reports `ACTIVE_HEALTHY`. Freshly created projects often show `pg_bouncer`/`pooler` UNHEALTHY for a few minutes; it resolves on its own — do not chase it or recreate the project.
6. **`SUPABASE_APPLY_A_MIGRATION` per file, in filename order.** Give each call `name` = file stem and a distinct `idempotency_key` so a retry cannot double-apply. On failure, report the SQL error verbatim and stop — never retry blindly.
7. **Verify with `SUPABASE_LIST_MIGRATION_HISTORY` and `SUPABASE_GET_TABLE_SCHEMAS`.** The apply response body alone is not proof; history plus schema is.
8. **`SUPABASE_GET_PROJECT_API_KEYS`** — set `reveal: true` only when plaintext is genuinely needed, and only then persist. Write URL / anon key / service role key into the env store atomically (tmp file → chmod 600 → replace → chmod 600), report only lengths and head/tail characters, then mirror the same vars into the deploy target and redeploy.
9. **Re-point the auth config at the real domain.** A fresh project ships `site_url = http://localhost:3000` and an empty `uri_allow_list`, which silently breaks every production redirect (OAuth callbacks *and* magic-link/OTP emails). Read it with `SUPABASE_GET_AUTH_CONFIG`, then set `site_url` to the public domain and `uri_allow_list` to a comma-separated list covering the custom domain, the stable deploy alias, and localhost. Inspect before writing — providers may already be enabled with valid credentials, and the fault is often only these two fields.

## Proving auth works without a browser

Configuring auth is not the same as verifying it. Three cheap probes cover the layers, and none needs a login:

- **Provider enablement — `GET /auth/v1/settings`** (with the anon key as `apikey`). Returns `external: {github, google, email}` booleans. This is the fast truth check for "is the provider actually on", cheaper and more direct than re-reading the management config.
- **Mail path accepted — `POST /auth/v1/otp`** with a real address returns `200 {}`. A 200 proves the request was accepted, *not* that mail was delivered (the built-in SMTP is rate-limited and not intended for public senders — see the SMTP note below).
- **The signup trigger actually fired.** Read the endpoint response alone and you have proven nothing about the database. Count across the boundary: `select (select count(*) from auth.users), (select count(*) from public.profiles)` via `SUPABASE_RUN_READ_ONLY_QUERY`. Equal non-zero counts prove the `after insert on auth.users` trigger created the profile row; a matching-join count and a non-null email prove it carried the fields over.

For the redirect layers (app site URL, provider `site_url`, IdP callback registration) and browser-free authorize probes, see the `vercel-feature-activation` skill's `references/oauth-provider-activation.md` — the layer model and the Google/GitHub probe asymmetry live there, not here.

A production sender needs custom SMTP configured in the provider's auth settings (host/port/user/key from a transactional mail provider, plus verified SPF/DKIM on the sending domain). Until that is set, treat email sign-in as functional-but-not-production and say so — the built-in mailer's limits are a delivery risk, not a configuration bug.

## Pitfalls

- Discovery → schema → execute is one session; splitting it across sessions loses the `session_id` that keeps the workflow bound.
- A project ref is 20 lowercase chars and appears in the database host (`db.<ref>.supabase.co`); derive the URL from the ref rather than re-listing.
- "Connection active" claims must be backed by a field in the latest output, not by the memory of having enabled the toolkit earlier.
- **Apply migration SQL read from the on-disk file, never retyped into the tool argument.** Hand-transcribing multi-KB SQL into a JSON string introduces escaping/quoting corruption that fails deep inside the database with a cryptic `invalid input syntax for type json`. Read `open(path).read()` in the same script that calls the tool; the file stays the single source of truth.
- **After applying, prove the DATABASE matches the FILE — an applied migration is not a faithful one.** A migration can report `success: true` while the rows that landed differ from the file (retyped or reshaped SQL), and nothing later catches it: the app renders from the content tree, the tests assert against the database, so both stay green while the two disagree. Compare them explicitly — count the rows the migration file creates, then query the live table and diff the identity column (e.g. the `jalur`/slug values), not just the totals. A count that matches while the identifiers differ is the failure signature: it means N rows exist but they are not the N the file defines.
- **Reconcile derived totals against the source of truth before trusting a green suite.** The schema's job is to mirror the content tree; the content tree is authoritative. When a seeded count exceeds the number of source documents, the surplus rows have no content behind them — progression and certificates will reference lessons that can never render. Report the gap with both numbers and both identity lists, and let the owner choose which side to align; do not silently re-seed either one.
- **Supabase tools are only reachable through `COMPOSIO_MULTI_EXECUTE_TOOL`.** A raw `tools/call` to `SUPABASE_APPLY_A_MIGRATION` returns "Tool not found" — the meta-tool wraps per-app tools. Wrap every call as `{"tool_slug": "SUPABASE_APPLY_A_MIGRATION", "arguments": {...}}` with `session_id` + `sync_response_to_workbench: false`.
- **`SUPABASE_GET_TABLE_SCHEMAS` requires a `table_names` parameter.** Omitting it returns 400 with "fields are missing: {'table_names'}" — fetch schemas for explicit tables or fall back to `SUPABASE_RUN_READ_ONLY_QUERY` against `information_schema`/`pg_catalog` for counts and structure.
- **`psql` connectivity checks to `db.<ref>.supabase.co` are not a reliable gate.** A `db_pass` generated for project creation may not authenticate direct `postgres` logins (pooler/Supabase free-tier routing). Test migrations through the Composio apply call + read-only query, not psql.
- **The auth-config tools live on the same meta-tool surface** as the project tools (reached the same way, per the pitfall above). `SUPABASE_GET_AUTH_CONFIG` is read-only — use it to establish current state before writing any auth setting.
- **OAuth provider callbacks are registered against the Supabase callback, not the app's.** The IdP must allow `https://<ref>.supabase.co/auth/v1/callback`. Pointing the IdP at the app's own `/auth/callback` produces `redirect_uri_mismatch`. Setting `site_url`/`uri_allow_list` does not fix that — it is a separate registration in the IdP console, and it is an owner action.
