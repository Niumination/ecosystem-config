# Restore repo layout — build side, restore side, and the contract between them

A restore that lives only as a plan is not a restore. The deliverable is a **private repo** plus the drill harness
that proves it, and the shape below is what survived contact with a real end-to-end drill.

## Two sides, two homes

| Side | Lives in | Runs on | Reads |
|---|---|---|---|
| **BUILD** | the ecosystem's own `scripts/` (or equivalent), under version control | the live machine | real files: `~/.ssh`, `~/.9router`, app state dirs, signing keystores, launchd plists |
| **RESTORE** | the private restore repo | a blank/fresh machine | the repo contents + release assets |

Dependency direction is one-way: BUILD writes into the repo; the repo never reads the build scripts. Keep it that
way or nothing about the restore can be trusted independently.

## Repo layout that works

```
restore-repo/
├── README.md              prerequisites, restore order, per-platform status table
├── MANIFEST.md            every entry + why it cannot be rebuilt
├── RESTORE-PATHS.md       repo path -> destination path on the new machine
├── restore.sh             orchestrator: DRY-RUN by default, fails hard
├── verify.sh              proves the result; reads only what it must
├── scripts/
│   ├── fetch-release.sh   download + rejoin release-hosted blobs, verify checksum
│   ├── subst-paths.sh     path/username substitution, allowlist-driven
│   ├── allowlist-paths.txt   GENERATED by build, not hand-written
│   ├── old-home.txt          the source machine's home path (basis for user rename)
│   └── services/          per-OS service installers + templated unit files
├── hermes/                identity files + local patches + APPLY.md
├── credentials/           *.enc (ciphertext only)
└── l2-data/               large encrypted blobs, or release-hosted if oversized
```

## Restore order (dependency chain — do not reorder)

1. **Clone the code/config repos first.** `git clone` refuses a non-empty destination, so anything that writes into
   the target tree earlier (decrypted secrets, extracted blobs) blocks it. Ecosystem repo becomes the root; nested
   repos (dotfiles) clone *into* it after, because the parent ignores that path.
2. **Application import** (`hermes import --force`) — restores config, `.env`, auth, skills, cron, state DB.
3. **Fix symlink-backed identity files.** An importer that walks a tree skips symlinks, so an identity file that was
   a symlink on the source returns as the application's default. Recreate the link to the freshly cloned repo and
   check by hash.
4. **Credentials** — decrypt into place, `chmod 600`.
5. **Data blobs** — decrypt + extract to their original (ignored) paths.
6. **Substitution** — rewrite paths for this machine.
7. **Verify** — only in apply mode, and its failure must exit non-zero.

## The build/restore contract

Diff the two sides mechanically before trusting them:

```bash
# every filename the writer emits must be named in the reader
grep -rn 'openssl' <build-scripts> <restore-repo>/*.sh <restore-repo>/scripts/*.sh
```

Two classes of drift cost real time and are invisible in a green run:

- **Names and extensions.** Writer emits `*.enc`, reader globs `*.age` → zero iterations, logged as done. Writer
  produces `x.tar.zst.enc`, reader looks for `x.tar.zst.age` → payload silently skipped. Make "processed zero items"
  a hard failure wherever payload was expected.
- **KDF parameters.** `openssl enc` stores salt, not iterations. `-iter 200000` on write and the default (10000)
  on read fails on every file, on the target, once the original is gone. Declare the parameter once and share it.

Also verify the *destination* of each decrypted file: a target that resolves to a directory path where a file
belongs writes the payload in a way nothing later reads.

## Release-hosted blobs

Anything over the host's per-file cap (GitHub: 100 MB) goes to release assets, never to a commit.

```bash
split -b 45m -d -a 2 payload.zip payload.zip.part-   # numeric suffix, rejoin sorts numerically
shasum -a 256 payload.zip > SHA256SUMS
git push && gh release create <tag> --repo <owner/repo> payload.zip.part-* SHA256SUMS
```

On the reading side: download with the label, rejoin by **numeric** sort, then verify against `SHA256SUMS` and fail
loudly on mismatch. Always pass `--repo` explicitly — a release command that derives its target from `$PWD` has
published to the wrong repository before.

## Generating the substitution allowlist (both directions of path drift)

The allowlist is build output, not a hand-maintained list, and it needs **two** substitutions:

- **Placeholder mode** — text files that were rewritten to `{{HOME}}`/`{{ECO}}`/`{{HERMES_HOME}}` when staged into
  the blob are restored to real paths.
- **Rename mode** — files that ship *with the code* (cloned repos, tracked configs) still contain the old absolute
  home. Compare the recorded old home against the new `$HOME`; when they differ, rewrite the old prefix everywhere in
  the allowlist. Without this a new machine with a different username keeps a tree full of dead absolute paths.

Generate the list by scanning only what actually needs it (blob staging results + `git ls-files` output that contains
the old home), and have the substitution step verify **only the files in the allowlist** — a whole-tree placeholder
check finds the plan documents that *describe* placeholders as examples and reports them as failures.

## Drill harness

Make the drill a script, not a sequence of remembered commands:

1. Clone the restore repo **from its remote** into a temp dir (never a local working copy).
2. Fetch the release-hosted blob via the repo's own `fetch-release.sh` (this exercises the join + checksum path).
3. Run `restore.sh --apply --target-home <temp>/home` against a clean HOME.
4. Read the per-step log; the orchestrator's own verify step is the verdict.
5. Delete the temp HOME afterwards — it now contains every secret in cleartext.

Budget wall-clock before promising anything: measure throughput against the same host first (a plain HTTPS fetch of a
similar-sized object is the control). A multi-hundred-MB payload on a slow link is hours, not minutes, and the
honest conclusion may be to carry the blobs on physical media instead of re-downloading them.

## Keeping the snapshot fresh (the part that decides whether it still works next month)

A restore repo is a **snapshot, not a live sync**. Nothing inside it pulls changes from the machine; it only changes
when the build side runs. State that plainly in the repo's own docs, because the failure mode is silent and slow: the
machine keeps changing, the snapshot quietly ages, and the gap is discovered on the day the machine dies.

Structure it so freshness is one command, not a remembered sequence:

- One entry point on the build side (`sync-all.sh`) that runs every layer builder in order, aborts on the first error,
  commits **selectively** (never `git add -A`), pushes, and prunes old large releases.
- A `--dry-run` that only checks prerequisites (credentials reachable, token valid, passphrase retrievable) — this is
  what an unattended run fails on first, and the failure must be loud, never a skipped step.
- Document **what triggers a refresh** as a concrete list tied to real events: a new API key, a new skill, a new
  project carrying its own `.env`/keystore/DB, a changed signing key, a config change, plus a weekly floor for when
  nothing obvious happened. The trigger list is what stops "I added a key three weeks ago" from being a surprise.
- Prune by policy: large release assets accumulate one full copy per refresh, so keep the last N and delete the rest
  in the same command that creates them.
- Name the growth cost honestly in the docs: a binary layer committed to git adds its compressed size to history on
  **every** refresh, so the shallow clone a new machine performs grows monotonically. Record the number and the
  escape hatch (move that layer to release assets) even while it is still small.
- Refresh on demand before any planned migration, and treat "the drill has not been re-run since the last change" as
  the same as untested.

Prefer a scheduled job on the platform's existing scheduler over a filesystem watcher or a new daemon: the ecosystem
rule against standing processes exists because every extra watcher competes for RAM and fires on every save.

For a deterministic refresh, schedule it **without an agent** where the scheduler supports it (a script-only job whose
stdout is delivered verbatim): no token cost, and — the part that matters — no dependency on model quota, so the backup
does not stop working the week the model is unavailable. Reserve agent-scheduled variants for jobs that genuinely need
judgement.

Measure what a non-interactive process can actually reach instead of assuming. On macOS, `security
find-generic-password` **works** from a background job (verified, exit 0) — but a CLI that keeps its own copy in the
keyring is a separate matter: a revoked token there surfaces as `Bad credentials`, which reads like a permissions
problem and is not. Give the job the credential path it can really use, and make an unreachable credential a loud
failure rather than a silently skipped layer.
