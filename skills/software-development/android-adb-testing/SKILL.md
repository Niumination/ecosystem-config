# Android ADB On-Device Testing

## Procedure

Defects found during on-device testing get fixed in the app or CI, not handed to the owner as manual on-device recipes — a terminal workaround is the last resort for unblocking today, never the plan of record; if one is given, file the app-side fix as the follow-up in the same session.

1. Verify transport: `adb devices -l` must show the device as `device` (not `unauthorized` — that means the phone-side RSA dialog is still pending).
2. Read device facts one property per call (`getprop` takes a single argument): `ro.product.model`, `ro.build.version.release`, `ro.build.version.sdk`, `ro.product.cpu.abi`.
3. Check installed state: `adb shell dumpsys package <id> | grep -E "versionName|versionCode"`. Same version does NOT mean same binary — identify the on-device binary by pulling its APK (`adb shell pm path <id>`, then `adb pull`) and comparing its signer-cert SHA-256 against the candidate artifact (scan APK bytes for X.509 certs); versionName and byte size are both weak identity evidence and have falsely matched different-signed builds.
4. Update with `adb install -r <apk>` — data survives, so multi-hundred-MB downloaded runtimes are kept.
5. `INSTALL_FAILED_UPDATE_INCOMPATIBLE` means the installed APK was signed with a different key — NEVER auto-uninstall; ask first, because uninstall wipes app data including downloaded runtimes. CI `assembleDebug` with no committed keystore mints a fresh debug key on every runner, so consecutive CI builds NEVER update each other — pin one stable key (`keytool -genkeypair -storetype JKS`, alias `androiddebugkey`, password `android`), record its SHA-256 fingerprint at generation time, keep it ONLY as a repo secret (shred every local copy once set), and wire it EXPLICITLY: decode the secret to `$RUNNER_TEMP`, point an explicit debug `signingConfig` at that path via env, and gate the job with an artifact check that fails the build unless the APK carries the pinned fingerprint (scan the APK bytes for X.509 certs, compare SHA-256). Never rely on implicit `~/.android/debug.keystore` pickup — it silently no-ops on some runners, and two green builds then ship different keys with no error anywhere in the log.
6. Launch: `adb shell monkey -p <id> -c android.intent.category.LAUNCHER 1`; confirm the foreground screen with `adb shell dumpsys activity activities | grep -E "mFocusedApp|ResumedActivity"`.
7. Logs: `adb logcat -c` BEFORE the user action, then `adb logcat -d` after — prefer `--pid=$(adb shell pidof <id>)` over tag grep, and exclude vendor noise (thermal, hiber, GnpSdk).
8. Screenshots come from the DEVICE (`adb exec-out screencap -p > shot.png`) — this works headless; macOS `screencapture` needs a lit local display (brightness above 0% — a fully-dimmed screen fails exactly like sleep/lock) and is the wrong tool for phone screens.
9. Verify every step before directing the next: after each on-device action pull a fresh screenshot AND a targeted logcat window, confirm the visible state matches the expected step, and only then tell the user what to tap next — never chain two user actions on an unverified assumption.
10. For guest-process failures (installer, runtime CLIs), check the app's own output files before logcat: `adb shell run-as <id> ls cache/` for `runtime-output-*.log` — these hold the tool's stdout/stderr that logcat never carries. Grab them in the SAME pass as the screenshot; the app may rotate/clean cache between runs, so a second attempt minutes later finds nothing.
11. When `INSTALL_FAILED_UPDATE_INCOMPATIBLE` forces an uninstall, preserve app-private data first — see [App-Data Backup & Restore](references/app-data-backup-restore.md) for the run-as tar-pipe recipe (backup → verify contents → uninstall → install → rooted restore). Never skip the content check: a 0-byte or key-missing archive means the pipe failed silently.
12. When the on-device config itself is suspect (wrong base URL, model, protocol the user typed), read it from the app instead of asking: `adb shell run-as <id> cat shared_prefs/<prefs>.xml` shows provider base/kind/model/protocol and feature flags. Strip secret values from anything you quote back — grep out `api_key|token|secret|password` lines, and for encrypted vault files list only entry NAMES (`grep -oE 'name="[^"]+"'`) to prove a key EXISTS without ever reading its value.
- When the user reports an on-device error, exhaust device-side evidence before asking for on-screen details: setup-state.json status/progress, setup-log tail, a pid-filtered logcat window covering the incident, non-secret prefs keys, and guest marker/binary state, and the persisted chat transcript JSON (`workedMillis` plus work-item titles distinguish an 11ms spawn-death from a 40s mid-run kill without any logcat). Ask for a screenshot or exact message text only when that set cannot name the failure — the phone is instrumented, the user's verbal description of the screen is the weakest sensor.
- When two consecutive fix→green-CI→device-fail cycles produce no behavior change, stop patching and re-diagnose from device evidence before the next code change — reread the persisted session JSON (mtime plus content proves whether the send path even ran), the latest runtime-output file (proves whether the guest tool answered), and the UI event-gate state; a third blind patch burns another full CI-plus-download cycle while the evidence already names the failing layer.
14. Request a phone test run only after local rehearsal plus green CI — the on-device loop costs a multi-minute download and the user's hands, so never spend it verifying what a unit test or lint job could have caught.

## Pitfalls

- `install -r` preserves data, which is wrong for from-scratch onboarding tests — use `adb shell pm clear <id>` instead, but warn it re-triggers large downloads.
- Device `localhost` is the phone itself — never point app endpoints at `http://localhost` expecting a Mac-side service; use the Mac's LAN IP.
- When the device list is empty, check the phone-side allow dialog and cable before restarting the server.
- `run-as` file forensics inside proot-managed trees can lie: `ls` may list entries that `stat`/`cat` then report as missing (mount-namespace/symlink artifacts) — when listing and stat disagree, abandon shell file checks and switch evidence to app-observable behavior (logcat for the app PID, UI state).
- Never ask the user to paste secrets they typed on-device (API keys stay on the phone); verify through masked-field screenshots and the server's own response messages instead.
- Read the app's fallback chain in source before probing the device — a guest-install error names only the LAST fallback tried (`pip: command not found` means `python3 -m pip` and `pip3` were already ruled out), so the fix must satisfy the first missing link, not the named one.
- Check the package's Requires-Python floor on PyPI before prescribing an on-device interpreter upgrade — when every release shares the same floor, pinning an older version cannot help and only the interpreter must change.
- Pass absolute paths to `run-as` — never `cd`. Its cwd is ROM-dependent (app dir on some builds, `/` on others) and compound `sh -c "cd … && …"` strings mis-execute; `run-as <pkg> tar -czf - /data/…` with absolute members always works.
- A `run-as` `Permission denied` on paths it read moments ago is usually the ROM dropping the call to shell (check `id` — uid 2000 instead of the app uid), not a real ACL change — retry the identical call before rerouting the investigation.
- `run-as` reads but cannot EXECUTE app-private binaries: `run-as <pkg> python3 -c ...` fails with `exec failed for python3: Permission denied`, so never plan to run an interpreter on-device — `cat`/pull the file and parse it on the host. Locate markers and config with `run-as <pkg> find files -maxdepth 3 -name '<marker>'` instead of guessing a HOME-relative path: the rootfs root and the guest HOME are different directories, and a miss at the assumed path proves nothing.
- Byte-identical consecutive `screencap`s mean a dozed/locked display, not a frozen app — send `KEYCODE_WAKEUP`, re-capture, and md5-compare before spending vision on the frame.
- When the guest distro is EOL and its package sources no longer carry a newer Python (confirm via the PPA/repo dist list, not by retrying apt), stop fighting apt — install a standalone interpreter with uv (`python3 -m pip install uv`, `uv python install <ver>`, symlink the versioned binary onto PATH) and point the installer at it; install console scripts with `uv tool install --python <ver>` so the entry point lands in `~/.local/bin` where app verifiers look; force `UV_LINK_MODE=copy` (or `--link-mode copy`) because PRoot's link2symlink mode rejects hardlinks with `Operation not permitted`; third-party Python repos drop EOL releases without warning.
- Rehearse generated guest-shell logic locally before burning CI cycles: `bash -n` the assembled script for syntax, and execute the selection functions against stub binaries on PATH (tiny scripts echoing fake `sys.version_info` numbers) to prove pick/fallback/empty branches — a green local rehearsal plus a repo unit test on the script builders catches quoting and branching bugs the compiler cannot.
- Never push an APK update while a guest install is in progress — reinstalling kills the running guest processes and wastes a multi-minute download; queue the deploy until the on-device run completes or fails (confirm via `ps` that no guest installer remains).
- Split multi-minute guest operations into staged steps with progress emission per stage — a single long guest call produces exactly one progress event, so the settings progress bar freezes at its initial fraction and the install looks dead-stuck while work proceeds normally in the background.
- Host-side checks of guest-installed binaries must resolve absolute symlinks inside the rootfs — `File.canExecute()` follows them against Android's host root and always reports false outside PRoot, so a present-and-working binary reads as 'not installed' and every tap re-runs the installer.
- When the APK carries no `META-INF/*.RSA|*.DSA` (APK Signature Scheme v2/v3-only signing), extracting a cert for keytool yields an empty file — do not read that as 'unsigned'; find the signer by scanning the APK bytes for X.509 certs (or apksigner), and treat a trial `adb install -r` as a safe signature-compatibility probe since a key mismatch fails the install without touching app data.
- When one host-side check on a guest path proves wrong, grep every sibling check on the same path in the same session — installed-state, version-list, and update-verifier each embed their own copy, and fixing one while a second still uses the raw check leaves one screen reporting 'not installed' for a working binary.
- When splitting or moving shell-in-Kotlin blocks, copy the block verbatim from git instead of re-escaping by hand — one doubled backslash turns a literal `\$` into a Kotlin template reference and fails CI with Unresolved reference. After ANY hand edit touching `\` or `$` inside Kotlin string literals, `git diff` the hunk and compare every escape against adjacent known-good lines before pushing — a doubled backslash is invisible at a glance and only surfaces a full CI cycle later. When the diff itself is ambiguous about doubling, verify bytes with `git diff | cat -A` or `od -c` on the file region — the patch tool lands exactly what you type with no auto-escaping, so trust the bytes, not your reading of the diff.
- After adding an enum entry, grep every exhaustive `when` over that enum before pushing — CI compiles all flavors and one missing branch fails the whole run; one grep saves a full CI cycle.
- Attribute server-side rejections only after an independent live probe reproduces them — send the same endpoint/method/headers via curl from Mac and read the exact error body, because a single 429 never proves a tier is dead when quotas vary per model and minute (rotate to another live model ID from the models list before declaring outage); keyless relays may also require affinity headers the app does not send yet, which probes as a 400/MissingSessionID rather than an auth failure.
- A present `~/.local/bin` entry plus a missing version marker does NOT mean 'healthy, just unmarked' — verify the link TARGET inside the rootfs (`readlink` the symlink, then `ls` the re-rooted target): a `uv tool install` that died mid-run leaves a dangling symlink into a `~/.local/share/uv/tools/<pkg>/bin/` holding only activate scripts and no entry-point binary. Husk (dangling link, no binary, no marker) means full reinstall; only a working binary with a lost marker qualifies for marker self-heal.

- Cover BOTH provider UI surfaces when changing gating or validation — Settings and the onboarding Step-3 flow each carry their own copy of the key field, model field, and enable-gates, so a keyless exemption fixed in one still blocks the other behind a mandatory key field.
- Read the phone screen yourself before asking the user to describe it — pull `adb exec-out screencap` and inspect the frame with vision; the exact on-screen step, field contents, and error text name the failure faster than any verbal report, and asking for a description first wastes the ADB link you already hold.
- Treat silent session/chat failures as a display-gate problem until proven otherwise — when the bridge emits a failure reason but no toast or bubble appears, grep the toast/message filter predicates for the reason substring; a reason matching no gate fails invisibly.
- Route contributor-tier free models around their non-interactive refusal — one-shot runs against training-on-data tiers exit without answering unless the guest config sets the consent flag, so default free presets to a no-consent model or ship an explicit opt-in toggle that writes the flag into the guest config with the training disclosure attached.
- Resolve on-device marker/config paths from the installer's code definition before declaring anything missing — markers may live at the rootfs root while binaries live under the guest HOME, so a `cat` at the assumed HOME-relative path proves nothing; grep the marker's base-dir constructor in source first.
- When a guest CLI works on the host but dies on-device, simulate first-run on the host with a clean HOME before blaming the device — identical behavior under a fresh HOME clears bootstrap/config-init as the cause and points at spawn, env, or transport instead.
- Never count guest processes with a bare `ps ... | grep -c <pattern>` — the grep itself matches the pattern and inflates the count; use `grep <pattern> | grep -v grep` or the `[p]attern` self-exclusion trick, or a stuck-install verdict is drawn from your own pipe.
- Never persist chat/transcript placeholder items under a fixed ID from a writer that runs on every event — each write appends another same-ID row and the list crashes with a duplicate-key FATAL that kills the live session; suffix generated IDs with a timestamp, strip stale placeholders before appending, and guard the load path with a dedupe-by-ID so old files cannot crash the renderer on next launch.
- When a chat session dies with no failure reason anywhere, check pid-filtered logcat for FATAL EXCEPTION before blaming model, network, or spawn — an app crash mid-session looks exactly like a silent agent failure, and the stack trace names the real killer.
